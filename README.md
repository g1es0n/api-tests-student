# API-тесты TestBoard

Лабораторная работа на базе `api-tests-student`: создание объявлений и работа с избранным.

- [Тестовый стенд](https://testboard.avito.com/)
- [Swagger](https://testboard.avito.com/swagger/index.html)
- [Исходный шаблон](https://github.com/qa-course-avito/api-tests-student)

## Подготовка

1. Установите Git, Go 1.25.1 или выше и [golangci-lint v2](https://golangci-lint.run/docs/welcome/install/local/).
2. Склонируйте свой публичный fork и перейдите в его корень:

```powershell
git clone https://github.com/<ваш-логин>/api-tests-student.git
cd api-tests-student
git switch main
go mod download
```

3. Зарегистрируйте основной аккаунт на TestBoard. Создайте в корне `.env.override`:

```dotenv
API_URL=https://testboard.avito.com/api/v1
TEST_LOGIN=your_email@example.com
TEST_PASSWORD=your_password
DEBUG=false
```

`.env.override` перекрывает `.env` и не включается в Git. Для запуска нужен доступ к стенду, включая регистрацию пользователей.

Необязательно можно указать отдельного продавца:

```dotenv
TEST_SELLER_LOGIN=seller_email@example.com
TEST_SELLER_PASSWORD=seller_password
```

Если обе переменные продавца не заданы, helper вычисляет его учётные данные из основного логина и пароля и регистрирует аккаунт. При повторной регистрации с ответом 409 выполняется вход. Продавец создаёт объявления для сценариев создания и избранного.

## Запуск

Все тесты без кэша:

```powershell
go test -count=1 -v ./...
```

Три повторения каждого пакета для проверки стабильности; пакеты могут выполняться параллельно:

```powershell
go test -count=3 -v ./...
```

При ограничении частоты запросов можно уменьшить нагрузку, выполняя пакеты последовательно:

```powershell
go test -count=1 -v -p 1 ./...
```

Отдельные пакеты:

```powershell
go test -count=1 -v ./tests/scenarios/createAdvertisement/
go test -count=1 -v ./tests/scenarios/favorites/
go test -count=1 -v ./tests/scenarios/advertisementSearch/
go test -count=1 -v ./tests/scenarios/myAdvertisement/
```

Линтер и проверка компиляции без запросов к API:

```powershell
golangci-lint run
go test ./... -run '^$'
```

Для сохранения полного вывода в PowerShell:

```powershell
go test -count=3 -v ./... *> review-tests.log
$LASTEXITCODE
```

Код завершения должен быть `0`, все четыре пакета сценариев должны завершиться строками `ok`. `-run '^$'` проверяет только компиляцию и не подтверждает прохождение API-тестов.

## Покрытие задания

| Требование | Файл в `tests/scenarios` | Проверки |
|---|---|---|
| Создание со всеми параметрами | `createAdvertisement/create_positive_test.go` | 201; title, description, price, quantity, владелец; чтение по ID; поиск по полному названию и ID; количество и ID фотографий, непустые URL |
| Невалидные параметры | `createAdvertisement/create_validation_test.go` | 400 и `invalid_request`, сообщение содержит проблемный параметр: пустой title/description, отрицательная цена, title из 51 символа, отсутствие фото, 4 фото |
| Граница длины title | `createAdvertisement/create_title_boundary_test.go` | Создание с 50 символами, включая кириллицу; сохранение параметров |
| Создание без авторизации | `createAdvertisement/create_unauthorized_test.go` | 401 для отсутствующего и неверного токена; проверка тела ошибки |
| Добавление и удаление избранного | `favorites/favorites_lifecycle_test.go` | Созданное объявление появляется в списке и исчезает после удаления из избранного |
| Удаление самого объявления | `favorites/favorites_deleted_ad_test.go` | Объявление было в избранном; после удаления владельцем отсутствует |
| Добавление несуществующего ID | `favorites/favorites_add_missing_ad_test.go` | 404 и сообщение об отсутствии записи |
| Удаление несуществующего ID | `favorites/favorites_remove_missing_ad_test.go` | 404 и сообщение об отсутствии записи |
| Избранное без авторизации | `favorites/favorites_unauthorized_test.go` | GET, POST и DELETE: 401 с отсутствующим и неверным токеном |
| Повторное добавление | `favorites/favorites_duplicate_test.go` | 409 и сообщение о повторном добавлении |
| Добавление собственного объявления | `favorites/favorites_own_test.go` | 403 и сообщение о собственном объявлении; оно не появляется в избранном |
| Пустой advertisement_id | `favorites/favorites_missing_id_test.go` | 400 и сообщение `invalid UUID length: 0` |
| Лимит 50 записей | `favorites/favorites_limit_test.go` | 50 успешных добавлений; 51-е возвращает 400 с сообщением о лимите; после освобождения места добавление успешно |

Дополнительно сохранены сценарии поиска по началу, середине, концу и разному регистру названия, а также проверки списка собственных объявлений и его авторизации.

В актуальном Swagger получение и удаление объявления используют `GET /advertisement?id=…` и `DELETE /advertisement?id=…`, а не путь `/advertisement/{id}` из формулировки задания. Для создания стенд ограничивает title 50 символами: тесты проверяют границы 50/51. Ограничение 255 в схеме `UpdateAdvertisementRequest` относится к другому запросу.

## Изоляция и очистка

- Каждый сценарий создаёт необходимые объявления сам. Названия содержат случайный суффикс, фотографии генерируются как PNG в памяти.
- Каждый сценарий избранного регистрирует отдельного покупателя с пустым избранным. Старые записи основного аккаунта и параллельные прогоны не влияют на лимит или выдачу.
- Тест собственных объявлений регистрирует отдельного владельца и проверяет ровно два созданных объявления: ID, владельца, даты, переданные параметры и фотографии.
- Поисковые тесты создают своё объявление перед каждым тестовым методом. Каждый поисковый фрагмент уникален для этого объявления, поэтому результат не зависит от заполнения первой страницы общего каталога.
- Менеджеры сразу после успешного создания регистрируют `t.Cleanup`. Удаляются только записи текущего теста, в том числе при последующем падении проверки. Уже удалённые записи допускаются при очистке; остальные ошибки очистки приводят к падению теста.
- Отдельные аккаунты остаются на стенде: обычный пользователь не имеет права на административное удаление аккаунтов. Объявления и избранное очищаются. При принудительном завершении процесса выполнение `t.Cleanup` не гарантируется.

Тест лимита создаёт 51 объявление и затем удаляет их, поэтому занимает заметную часть времени прогона. Он не использует чужие записи каталога. Проверяется именно ограничение `POST /favorites`; чтение списка из 50 записей не требуется для проверки этого ограничения.

## Архитектура и диагностика

`internal/client/http` отправляет HTTP-запросы → `internal/managers` проверяет ответы, разбирает модели и регистрирует очистку → `tests/scenarios` описывает бизнес-сценарии. Общие проверки находятся в `internal/assertions`, значения ограничений и ошибок — в `internal/constants`, генерация данных — в `internal/helpers`.

Логи отмечают подготовку (`Precondition`), действия (`Step`), проверки (`Check`), очистку (`Cleanup`) и повторы (`Retry`). Проверки негативных ответов учитывают ожидаемый HTTP-статус и содержимое ошибки.

При 429/503 клиент выполняет до пяти попыток с увеличивающейся паузой. Это ограниченные повторы ответа сервера; ошибки DNS/TLS и постоянные ошибки сервера остаются причинами падения. Повтор не превращает неверный результат проверки в успешный.

`DEBUG=true` в `.env.override` включает HTTP-логи. Они могут содержать токены и учётные данные; не публикуйте такой вывод.

## Сдача

Работа сдаётся в ветке `main` своего публичного fork, отдельный PR не нужен. После успешных трёх прогонов и `golangci-lint run` проверьте изменения через `git status` и `git diff`, закоммитьте исходники и README и выполните `git push origin main`. Файл `.env.override` и диагностические логи не должны попадать в коммит.
